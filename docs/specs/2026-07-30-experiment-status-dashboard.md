# 에이전트 실험 상태 대시보드 — 기본 기능 3개 (#338)

> 2026-07-30 · 이슈 #338 · 상태: 기본 기능 구현 완료(노출·저장 백엔드는 후속)

## 문제

에이전트가 실험을 수행할 때 **사람이 지금 무엇을 하고 있는지 볼 방법이 없다.**
가설 제출 후 중간 진행과 최종 결과를 알려면 로그를 직접 뒤져야 한다.

14회차 멘토 피드백(2026-07-23)의 접근을 그대로 따른다 — "가장 기본 기능이 뭔데?"부터
정의하고 확장은 그 다음이다.

## 기본 기능 3개

| # | 기능 | 계약 |
|---|---|---|
| ① | 가설 제출 | `POST /experiments` → 실험 id 발급 |
| ② | 진행 상태 조회·보고 | `POST /experiments/{id}/status`(에이전트) / `GET /experiments/{id}`·`GET /experiments`(사람) |
| ③ | 최종 리포트 | `POST /experiments/{id}/report` → 상태 종료 |

화면은 `GET /experiments/ui/dashboard` 한 장(목록: id·제목·상태·단계·진행·판정·갱신).

## 설계 결정

### 1. 이벤트가 사실이고 상태는 뷰다

실험 상태를 갱신하는 대신 **append-only 이벤트**(`submitted`/`status`/`report`)만 쌓고,
조회 시마다 상태를 파생한다. 근거: 에이전트 루프는 재시도로 단계를 되돌리는 것이 정상
경로이므로 "현재 상태" 필드를 덮어쓰면 이력이 사라진다. 이벤트가 남으면 나중에 소요
시간·재시도 횟수 같은 분석을 코드 변경 없이 얻을 수 있다.

파생 규칙:

- `report` 있음 → verdict가 `error`면 `failed`, 그 외(`supported`/`rejected`/`inconclusive`)는 `succeeded`
- `status` 있음 → `running`
- 그 외 → `submitted`

**`rejected`는 실패가 아니다.** 가설이 기각된 것은 실험이 정상적으로 결론에 도달한
것이므로 `succeeded`로 둔다. 이 구분이 대시보드 집계의 의미를 바꾼다.

### 2. 상태(enum)와 단계(자유 서술)를 분리

`state`는 고정 enum 4개(`submitted`/`running`/`succeeded`/`failed`)로 두어 대시보드
필터·집계의 기준을 안정시키고, `stage`는 60자 이내 자유 문자열로 둔다. 에이전트 루프가
바뀌어도 enum은 그대로 두려는 의도적 분리다. 단계 목록을 enum으로 고정하면 에이전트가
새 단계를 추가할 때마다 서버 배포가 필요해진다.

`progress`(0~1)는 선택이고 **단조 증가를 강제하지 않는다** — 재시도로 되돌아가는 것이
정상이기 때문이다.

### 3. 저장은 실험별 JSONL 파일, 백엔드는 교체 가능

MVP는 로컬 디스크(`AUTORESEARCH_EXPERIMENT_STORE_DIR`, 기본 `data/experiments`)에
실험 하나당 JSONL 한 파일이다. 새 인프라(DB·버킷)를 요구하지 않아 이 저장소 안에서
완결된다. 한계와 후속:

- **단일 프로세스 전제**다. 여러 워커가 같은 실험에 동시 append하면 seq가 겹칠 수 있다.
- 컨테이너 재시작 시 유실된다(emptyDir 기준). 영속화는 GCS·Cloud SQL 백엔드로 교체 —
  `JsonlExperimentStore`와 같은 인터페이스로 갈아끼우는 후속 이슈.

MLflow는 **리포트 아티팩트 저장소로만** 재사용한다(`artifact_refs`에 `runs:/...` 참조를
담는다). 실험 tracking과 겹치지만 "가설 제출 → 진행 → 리포트" 흐름은 MLflow UI에 없다.

### 4. 리랭킹 서빙과 별 앱으로 분리

`src/experiments/api.py`는 자체 `create_app()`을 제공하고 `src/serving/app.py`를
건드리지 않는다. 근거: 추론 지연이 중요한 표면에 대시보드 트래픽·저장 I/O를 섞지 않는다.
라우터는 `create_router(service)`로 분리해 두었으므로 나중에 합치기로 정하면 한 줄로
mount할 수 있다.

### 5. 인증은 이 앱에서 구현하지 않는다

기존 내부 UI 패턴(oauth2-proxy + 내부 ILB, `SKYAHO/Autoresearch-infra` 소유)을 재사용한다.
앱 자체는 인증 없이 ClusterIP로 두고 앞단 proxy가 Google 로그인·허용 이메일을 담당한다 —
Airflow(#48)·MLflow(#244)·Kibana(#293)와 동일한 구조다.

## 보안

- 실험 id는 파일명이 되므로 `^exp_\d{8}_[0-9a-f]{8}$`로 검증한다. 경로 조작 입력
  (`../etc/passwd`)은 디스크에 닿기 전에 400으로 거부된다.
- 대시보드 HTML은 사용자 입력(제목·단계)을 **전부 이스케이프**한다. 템플릿 엔진을 새로
  들이지 않고 `html.escape`만 쓴다.
- 모든 요청 본문은 `extra="forbid"` — 오타 필드가 조용히 무시되지 않는다.

## 후속 이슈로 분해

1. **영속 저장 백엔드** — GCS 또는 Cloud SQL 구현체 + 다중 워커 동시성(현재 단일 프로세스 전제)
2. **노출 경로** — 이미지·Deployment·Service·oauth2-proxy(인프라 저장소 연동)
3. **에이전트 연동** — 실험 루프가 실제로 status/report를 보고하도록 배선(에이전트 루프 소유)
4. **확장 기능** — 실험 이력 필터·검색, 가설별 성공/실패 판단 기준 표시, 중간 개입(중단/재시작),
   리소스 사용량. 이슈 #338의 확장 백로그 그대로

## 대안 검토 (이슈 본문 항목에 대한 결론)

- **Airflow UI·로그로 대체**: 부적합. 에이전트 실험은 DAG 단위와 1:1이 아니고 가설/리포트
  개념이 없다.
- **MLflow UI 확장**: 부분 채택. 리포트 아티팩트 저장소로는 재사용하되(위 3항), 제출→진행
  흐름은 별 표면으로 둔다.
