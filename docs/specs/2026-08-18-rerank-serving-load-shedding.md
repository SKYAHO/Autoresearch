# 리랭킹 서빙 부하 차단

## 목적

`POST /rerank`가 처리 용량을 넘는 트래픽을 받았을 때 **예측 가능하게 실패**하도록
만든다. 목표는 용량을 늘리는 것이 아니라, 규모와 무관하게 성립해야 할 설계 속성을
갖추는 것이다 — 한계를 넘으면 초과분만 즉시 거절되고, 받아들인 요청은 정상 응답
시간을 유지한다.

## 배경 — 측정으로 확인한 현재 거동

2026-08-18 로컬 개루프 측정(24후보, 워커 1개, 합성 모델)이다. 절대 수치는 GKE로
이전할 수 없지만, **실패 방식은 애플리케이션 코드의 성질이라 환경과 무관하다.**

| 도착률 | 실제 RPS | p50 | p95 | p95/p50 | 503 | 오류율 |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 140 | 140.0 | 5.2ms | 6.3ms | 1.2 | 0 | 0% |
| 180 | 180.0 | 5.3ms | 178.6ms | 33.8 | 0 | 0% |
| 220 | 166.1 | 2259ms | 5677ms | — | 0 | 0% |
| 260 | 158.1 | 2060ms | 14341ms | — | 0 | 0% |

세 가지가 드러났다.

1. **거절이 없다.** p95가 14초인 상태에서도 `503`이 0건이다. 요청은 거절되지 않고
   무한 대기열에 쌓인다. `--limit-concurrency`가 미지정이고, 동기 핸들러가 도는
   anyio 스레드풀(기본 40) 앞의 대기줄에는 길이 제한이 없다.
2. **겉보기로는 정상이다.** 180/s에서 p50은 5.3ms로 멀쩡한데 p95만 178.6ms다.
   오류율은 0%다. p50·평균을 보는 대시보드는 이 상태를 정상으로 읽는다.
3. **한계를 넘으면 처리량이 오히려 떨어진다.** 180 rps를 내던 서버가 220을 받으면
   166, 260을 받으면 158로 내려간다. 평탄한 천장이 아니라 congestion collapse다.

한계의 원인도 특정했다. 요청당 CPU가 5.79ms이고 응답 시간이 6.24ms로, **응답 시간의
93%가 계산**이다. `1초 / 5.79ms ≈ 173 rps`가 1코어의 이론상 최대이며 관측된 무릎
(140~180)과 일치한다. I/O 대기가 지배적이지 않으므로 비동기화는 해법이 아니다.

## 범위

동시 실행 상한과 요청 타임아웃을 도입해 초과분을 즉시 `503`으로 거절한다.

**범위 밖:**

- 워커 증설(`--workers`). 20코어 중 1코어만 쓰는 것은 이 측정에서 확인했으나,
  `prometheus_client`가 프로세스별로 메트릭을 들고 있어 `/metrics`가 워커마다
  달라지는 문제를 먼저 풀어야 한다. **용량을 늘려도 차단이 없으면 더 큰 규모에서
  같은 방식으로 무너지므로 순서상 뒤다.**
- replica·HPA·LoadBalancer (`Autoresearch-infra` 소유)
- 온라인 피처 캐시. 로컬에서는 조회 비중이 작지만 GKE에서는 다르므로 별도로 다룬다.

## 설계

### 동시 실행 상한

요청 검증 직후, readiness 판정 **앞**에서 동시 실행 수를 센다. 상한을 넘으면 즉시
`503`을 반환하고 핸들러 본문을 실행하지 않는다.

- 상한은 환경 변수 `RERANK_MAX_CONCURRENCY`로 주입한다. 미설정 시 차단하지 않는다
  (기존 동작 유지). **기본값으로 조용히 거동을 바꾸지 않는다.**
- 거절 판정과 카운터 증감은 원자적이어야 한다. 동기 핸들러가 여러 스레드에서 도는
  구조이므로 `threading.Lock`으로 보호한다.
- 거절 경로는 피처 조회·모델 예측을 하지 않는다. 거절 자체가 비싸면 과부하에서
  차단이 오히려 부하를 키운다.

### 요청 타임아웃

동시 실행 상한만으로는 부족하다. 상한 안에 들어온 요청이 의존성 지연으로 오래
붙잡혀 있으면, 그만큼 새 요청이 거절된다. `RERANK_REQUEST_TIMEOUT_SECONDS`를 넘긴
요청은 `503`으로 끊는다. 미설정 시 끊지 않는다.

### 응답 계약

`503`을 그대로 쓴다. `429`는 클라이언트별 할당량 초과를 뜻하고, 서버 전체의 일시적
과부하는 `503 Service Unavailable`이 표준 의미다.

- `Retry-After` 헤더를 함께 반환한다. 호출부가 고정 백오프 대신 서버가 제시한
  시각을 쓸 수 있다.
- `RerankRequest`/`RerankResponse` 스키마, 입력 순서 보존, 기존 422·503·500 의미는
  바뀌지 않는다. 과부하는 **새 상태 코드가 아니라 기존 503의 새 사유**다.

호출부는 이미 대응돼 있다. `autoresearch/recommendation/rerank_api.py`의 `rank_user`가
5xx를 `max_attempts`까지 백오프하며 재시도하고 4xx는 즉시 실패시킨다. **계약 변경
없이 기존 재시도 경로가 그대로 쓰인다.**

### 관측

`rerank_outcomes_total`에 `overloaded` 라벨을 추가한다. 기존 `unavailable`(readiness
실패)과 섞으면 대시보드에서 원인을 구분할 수 없다.

| outcome | 의미 |
| --- | --- |
| `success` | 정상 응답 |
| `unavailable` | 모델·FeatureStore 미준비 (기존) |
| `overloaded` | **동시 실행 상한 초과로 거절 (신규)** |
| `timeout` | **요청 타임아웃으로 중단 (신규)** |
| `feature_error` / `prediction_error` | 기존 |

라벨 카디널리티는 고정이며 user_id·video_id·예외 문자열을 넣지 않는다.

**차단이 관측되지 않으면 도입하지 않는 것과 같다.** uvicorn 내장
`--limit-concurrency`를 쓰지 않는 이유가 이것이다 — 애플리케이션 계층 밖이라 거절이
`rerank_outcomes_total`에 잡히지 않고 `Retry-After`도 붙일 수 없어, 차단이 실제로
작동하는지 증명할 수 없다.

## 폴백을 채택하지 않은 근거

"리랭킹 없이 원래 트렌딩 순서로 `200`을 반환한다"는 대안을 검토하고 기각했다.
서비스 가용성은 올라가지만 **일일 폐루프를 오염시킨다.**

노출 조립(`docs/specs/2026-07-22-model-exposure-assembly.md`)은 리랭킹 결과를 모델
노출로 기록하고, 그 노출이 action log가 되어 다음 학습 데이터가 된다. 모델이 고르지
않은 슬레이트를 모델 노출로 기록하면 **모델이 하지 않은 선택을 모델의 선택으로
학습**하게 된다. 과부하가 심할수록 오염 비율이 커지므로, 장애 상황이 곧 학습 데이터
품질 저하로 이어진다.

폴백을 도입하려면 응답에 degraded 표시를 넣고 노출 조립이 그것을 모델 노출에서
제외해야 한다. 공개 API 계약과 폐루프 양쪽이 바뀌므로 이번 범위에서 분리한다.
현재 호출부가 배치 하나뿐이고 재시도 경로가 이미 있으므로, `503` + 재시도로 충분하다.

## 검증

같은 하네스(`applications/reranking_api/loadtest/rerank.js`, `LOAD_MODE=open`)로 도입
전후를 **같은 조건**에서 비교한다. 판정 기준은
`docs/runbooks/rerank-loadtest.md` 5절을 따른다.

완료 조건:

- 한계를 넘긴 도착률에서 초과분이 `503`으로 거절되고, `rerank_outcomes_total{outcome="overloaded"}`가
  그만큼 증가한다.
- **받아들인 요청의 p95가 무릎 아래 수준을 유지한다.** 이것이 이 작업의 핵심 성공
  기준이다 — 거절 자체가 목적이 아니라 나머지 요청을 지키는 것이 목적이다.
- 상한 미설정 시 기존 거동과 측정값이 달라지지 않는다.
- 도입 전 실측표와 도입 후 실측표를 `docs/reports/`에 같은 스키마로 남긴다.
