Action Log 메모리 문제를
어떻게 고쳤나

12시간짜리 single-mode 실행에서 메모리가 계속 늘어난 이유와, 결과를 잃지 않으면서 메모리에 동시에 들고 있는 사용자 수를 제한한 bounded streaming 수정 내용을 한 장으로 정리한 문서입니다.

최종 커밋 e692219 브랜치 fix/393-action-log-memory-retention generated_at = 완료 시각 유지 Airflow 변경 없음

먼저 결론

문제는 Python의 free() 누락이 아니라, 끝난 사용자 결과를 계속 참조하던 구조였습니다. 이제는 사용자별 처리가 끝나는 즉시 이벤트를 임시 저장소에 기록하고 참조를 해제합니다. 따라서 실행 시간이 길어져도 메모리는 전체 사용자 수가 아니라 제한된 활성 사용자 수에 비례합니다.
250Mi → 502Mi기존 0~8시간 관측 증가
25~30Mi/h기존 시간당 증가 추정
4 × worker새 active-user 상한
50,000행최종 Parquet row group 목표

기존에는 왜 메모리가 늘었나

아래 그림에서 빨간 경로의 핵심은 “끝난 결과도 마지막까지 리스트에 남아 있었다”는 점입니다.

어떤 코드를 왜 바꿨나

코드 위치를 누르면 최종 커밋의 해당 파일로 이동합니다. 세부 계약은 승인된 spec에 있습니다.

pipeline.py · generate_action_log_single

1. 사용자 단위 bounded scheduler

전체 drafts를 만드는 대신 _StreamingUserState에 현재 활성 사용자만 보관합니다.

  • worker 수: max(1, max_concurrency)
  • active user 수: 4 × worker
  • Future는 worker 수만큼만 유지
  • 느린 첫 사용자가 있어도 window 안의 다른 work를 제출
pipeline.py · _StreamingActionLogWriter

2. 직접 Parquet 대신 임시 spool

사용자마다 최종 Parquet row group을 만들지 않고 Arrow IPC와 JSONL에 순서대로 기록합니다.

  • 최종화 때 최대 50,000행 단위로 Parquet 작성
  • Parquet row group 수가 사용자 수에 따라 폭증하지 않음
  • 성공 교체 전에는 임시 파일만 사용
  • 실패 시 기존 파일 rollback
pipeline.py · finalize 순서

3. generated_at 의미 복원

처음에는 streaming 시작 시각을 넣을 위험이 있었습니다. 이제 quarantine 검사까지 끝낸 뒤 한 번 계산합니다.

quarantine 검사 → generated_at = now(UTC)
→ IPC를 Parquet으로 최종화 → atomic publish

따라서 모든 row의 값은 기존 legacy처럼 “전체 생성 완료 시각”을 뜻합니다.

observability.py · ActionLogStreamingTelemetryReporter

4. 운영 중 메모리 상태를 JSON으로 출력

private _retention_observer는 테스트 hook으로 남기고, DAG에서는 같은 snapshot을 사용합니다.

  • action_log_streaming_progress
  • active user / buffered draft·event / in-flight work
  • completed / failed / pending work, throughput
  • latency p50/p95는 고정 크기 sample
pipeline.py · quarantine failure

5. 실패 산출물의 의미 분리

quarantine 비율이 한도를 넘으면 quarantine JSONL만 남기고 Parquet/warehouse는 성공 산출물로 publish하지 않습니다.

정상 성공 시에는 세 파일을 함께 publish하고, 중간 교체 실패면 기존 파일을 복구합니다.

pipeline.py · compatibility fallback

6. 기존 호출자 보호

exposure_metadata가 mutable mapping이 아니거나 user ID가 누락·중복이면 legacy batch로 fallback합니다.

정상 streaming에서는 drain된 사용자의 metadata entry를 제거하므로 해당 사용자 결과도 함께 수명을 다합니다.

무엇을 바꾸지 않았나

메모리 구조는 바꿨지만, downstream이 기대하는 논리 결과는 유지해야 했습니다.

이번 코드에도 남아 있는 가능성

1. 메모리 상한이 0은 아님

활성 사용자 window, 현재 사용자 청크, 최종화 중 최대 50,000행 buffer와 현재 IPC batch는 여전히 메모리를 사용합니다. 목표는 “일정한 상한”이지 “메모리 없음”이 아닙니다.

2. 느린 head는 backpressure를 만듦

window 안의 work가 모두 끝났는데 첫 사용자가 느리면 더 많은 사용자를 열지 않습니다. worker 활용보다 메모리 상한을 우선한 의도적인 trade-off입니다.

3. 파일시스템 장애는 별도 위험

atomic replace, backup 복구, 삭제가 실패할 수 있습니다. 원래 publish 오류를 보존하고 best-effort 진단을 남기지만, 운영자는 backup spool과 last-known-good 파일을 확인해야 합니다.

4. telemetry는 관찰 도구

logger나 telemetry sink 자체가 고장 나면 경고를 남기지 못할 수 있지만, 본 작업을 실패시키지 않도록 설계했습니다. 따라서 로그가 없다는 사실만으로 작업이 실패했다고 판단하면 안 됩니다.

5. 잘못된 metadata 입력은 legacy로 감

read-only mapping, 누락·중복 user ID는 호환성을 위해 legacy fallback을 택합니다. 이 경우 bounded streaming 메모리 특성이 적용되지 않을 수 있으므로 caller 계약을 지켜야 합니다.

6. 실제 12시간 plateau는 배포 후 확인 필요

로컬·CI 테스트는 구조와 계약을 검증합니다. GCP 프로젝트 autoresearch-503903의 Airflow 실제 run에서 progress 로그와 RSS/Grafana를 함께 확인해야 운영 결론을 낼 수 있습니다.

구현하면서 겪은 문제와 해결

문제 01

streaming으로 바꾸자 generated_at이 시작 시각이 됨
writer를 여는 시각에 값을 만들지 않고, quarantine 검사를 통과한 직후 한 번 계산하도록 이동했습니다.

문제 02

active user 수를 worker 수와 같게 묶어 head-of-line blocking 발생
worker 상한과 memory window를 분리하고 active user를 4 × worker로 늘렸습니다. Future 자체는 worker 수만 유지합니다.

문제 03

사용자마다 Parquet row group을 만들면 footer가 커짐
Arrow IPC spool에 먼저 쓰고, 최종화 때 50,000행 단위로 Parquet row group을 만들도록 바꿨습니다.

문제 04

새 경로에서 기존 운영 telemetry가 사라짐
retention snapshot을 structured event로 연결하고, 시작·종료 snapshot은 interval과 상관없이 강제 기록했습니다.

문제 05

telemetry/로그 실패가 원래 작업 실패를 덮을 위험
telemetry와 rollback 진단은 best-effort 경계로 격리했습니다. 원래 publish/quarantine 오류와 기존 파일 복구를 우선합니다.

문제 06

quarantine 초과 실행도 최종 Parquet을 다 쓴 뒤 실패
spool을 닫은 뒤 ratio를 먼저 검사하고, 초과 시 quarantine만 최종 경로로 이동합니다.

문제 07

리뷰 중 rollback logger handler가 예외를 던지는 경우 발견
진단 logger 예외를 별도로 삼켜 복구 loop가 계속 돌도록 보완하고, 원래 오류가 그대로 보존되는지 테스트했습니다.
