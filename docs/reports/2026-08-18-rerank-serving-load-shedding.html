Autoresearch · 리랭킹 서빙

과부하에서 조용히 무너지던 서빙에 부하 차단을 넣고, 전후를 같은 조건에서 쟀다

한계를 넘긴 리랭킹 서빙은 요청을 거절하지 않고 전부 느려졌다. 오류율은 0%였고 대시보드는 정상이라고 표시했다. 동시 실행 상한을 도입해 초과분만 즉시 거절하도록 바꾼 뒤, 실제 트래픽 조건에서 p95가 15.3초에서 233ms로 떨어졌다.

측정은 두 조건에서 했다. 200후보가 실제 호출부가 보내는 모양이고, 24후보는 가벼운 요청일 때의 대조군이다. 일일 추천 배치는 MAX_CANDIDATES_PER_REQUEST = 200으로 후보 200개를 한 요청에 담아 보내고, 그 순위 결과에서 24개를 골라 노출한다(모델 17 + 인기 5 + 탐색 2).

1. 도입 전 — 거절하지 않고 전부 느려진다

세 가지가 드러났다.

  • 거절이 없다. p95가 15초인 상태에서도 503이 0건이다. 요청은 거절되지 않고 무한 대기열에 쌓인다.
  • 겉보기로는 정상이다. 30/s에서 p50은 19.4ms로 멀쩡한데 p95만 84.1ms다. 오류율은 0%다. p50·평균을 보는 대시보드는 이 상태를 정상으로 읽는다.
  • 한계를 넘으면 처리량이 오히려 떨어진다. 40 rps를 내던 서버가 60을 받으면 30.5로 내려간다. 평탄한 천장이 아니라 congestion collapse다.

한계의 원인은 1코어의 계산 능력이다

24후보 조건에서 포화 시점의 서빙 프로세스 CPU를 /proc 델타로 재니 109%, 즉 1코어를 꽉 채운 상태였다. 요청당 CPU는 5.79ms이고 저부하 응답 시간은 6.24ms로, 응답 시간의 93%가 계산이다. I/O 대기가 지배적이지 않으므로 비동기화는 해법이 아니다. 1초 / 5.79ms ≈ 173 rps가 1코어의 이론상 최대이며 관측된 무릎(140~180)과 일치한다.

같은 머신에 코어가 20개 있지만 1개만 쓴다. --workers가 지정되지 않아 프로세스가 하나이고, GIL은 프로세스마다 하나이기 때문이다.

2. 서버는 자기 대기열을 보지 못한다

차이 = 대기열에서 보낸 시간             6,764 ms

rerank_duration_seconds 타이머는 스레드가 요청을 집어든 뒤에 시작한다. 그 앞의 대기열에서 보낸 6.7초는 서버 메트릭에 아예 기록되지 않는다. 대시보드에 이 지표를 띄워놨다면 250ms로 보였을 것이고, 실제 사용자는 7초를 기다리고 있었다. "거짓 정상"은 p50만의 문제가 아니라 서버 지연 메트릭의 구조적 사각지대였다.

k6가 재는 지연에는 거절된 503이 섞인다. 503은 피처 조회도 예측도 하지 않아 매우 빠르므로 섞인 채로는 p95가 실제보다 좋아 보인다. 위 표는 서버측 rerank_duration_seconds 증분이며, 차단 게이트가 타이머보다 앞에 있어 거절된 요청은 이 히스토그램에 들어가지 않는다 — 즉 정확히 "받아들인 요청"의 분포다.

4. 후보 수가 8배 달라도 같은 상한이 통한다

RERANK_MAX_CONCURRENCY = 4는 24후보 조건에서 정한 값이다. 한 요청의 무게가 8.3배인 200후보에서도 그대로 쓸 수 있는지가 설계 질문이었다. 도입 전에는 "동시 요청 수"가 아니라 "동시 영상 수 총합" 같은 가중치 제한이 필요할 수 있다고 보았다.

양쪽 모두 안정 구간에서는 한 건도 거절하지 않고 한계를 넘는 구간에서만 거절했다. Little의 법칙으로 설명된다 — 동시 실행 수는 도착률 × 응답시간인데, 24후보는 172 × 6ms ≈ 1, 200후보는 40 × 25ms ≈ 1로 양쪽 다 1 근처다. 후보 수가 달라도 한계 지점의 동시 실행 수는 비슷하므로 개수 기반 상한 하나로 충분하다. 가중치 제한이 필요할 것이라는 사전 우려는 측정으로 기각됐다.

5. 구현

결정근거
거절을 readiness·피처 조회·예측보다 앞에 둔다 거절 경로가 비싸면 과부하에서 차단이 오히려 부하를 키운다. 테스트로 "거절된 요청은 피처를 조회하지 않는다"를 고정했다.
세마포어가 아니라 Lock + 카운터 세마포어는 자리가 없을 때 대기하는 것이 기본이라 대기열을 없애려는 목적과 반대다. 여기서는 기다리지 않고 즉시 거절한다.
503 + Retry-After 429는 클라이언트별 할당량 초과를 뜻한다. 서버 전체의 일시적 과부하는 503이 표준 의미다. 호출부는 이미 5xx를 백오프하며 재시도하므로 계약 변경이 없다.
outcome="overloaded"·"timeout" 분리 기존 unavailable(readiness 실패)과 섞으면 같은 503이라 원인을 구분할 수 없다.
미설정 시 기존 거동 유지 기본값으로 조용히 거동을 바꾸지 않는다. 운영자가 명시적으로 켠다.
uvicorn 내장 --limit-concurrency를 쓰지 않음 애플리케이션 계층 밖이라 거절이 메트릭에 잡히지 않는다. 차단이 관측되지 않으면 도입하지 않은 것과 같다.

폴백을 채택하지 않은 이유

"리랭킹 없이 원래 트렌딩 순서로 200을 반환한다"는 대안을 검토하고 기각했다. 서비스 가용성은 올라가지만 일일 폐루프를 오염시킨다. 노출 조립은 리랭킹 결과를 모델 노출로 기록하고 그 노출이 action log를 거쳐 다음 학습 데이터가 된다. 모델이 고르지 않은 슬레이트를 모델 노출로 기록하면 모델이 하지 않은 선택을 모델의 선택으로 학습하게 되며, 과부하가 심할수록 오염 비율이 커진다.

6. 이 측정이 답하지 못하는 것

차단은 붕괴를 막지만 열화는 막지 못한다

200후보 30/s에서 도입 전후 p95가 84.1ms와 88.0ms로 같다. 거절이 0건이기 때문이다. 무릎 바로 위 구간은 대기열이 상한 4를 넘지 않으면서도 지연은 이미 4배로 뛴 상태라 차단이 개입하지 않는다. 상한을 더 조이면 이 구간도 보호되지만 정상 트래픽을 거절할 위험이 커진다.

  • 로컬 수치다. loopback이라 네트워크 왕복이 없고, GKE는 VPC 건너 Memorystore + TLS + IAM이다. 절대 수치는 이전할 수 없다. 다만 실패 방식은 애플리케이션 코드의 성질이라 환경과 무관하다.
  • 모델이 합성이다. 트리 200개·21개 피처 중 16개가 분기에 쓰이는 구조적으로 유효한 ONNX지만, model_predict 절대값은 champion과 다를 수 있다.
  • fixture 유저가 1명이다. Redis 엔티티 키가 하나뿐이라 캐시 지역성이 실제보다 유리하다.
  • 180/s(24후보)는 무릎 경계라 실행마다 흔들린다. 1차 178.6ms, 2차 8.4ms로 관측됐다. 확실한 비교는 붕괴 구간이다.

7. 측정으로 드러난 후속 항목

  • 워커 증설. 20코어 중 1개만 쓴다. 다만 prometheus_client가 프로세스별로 메트릭을 들고 있어 /metrics가 워커마다 달라지는 문제를 먼저 풀어야 한다. 용량을 늘려도 차단이 없으면 더 큰 규모에서 같은 방식으로 무너지므로 순서상 뒤다.
  • 후보 pool 크기. 200개를 전부 예측하지만 노출에 실제로 쓰이는 모델 순위는 상위 17개뿐이다. 후보를 줄이면 요청당 CPU가 줄어 한계가 올라간다. 다만 모델이 고를 폭이 좁아져 품질이 떨어질 수 있으므로 오프라인 평가로 재야 하는 ML 문제다.
  • 하네스의 오류율 게이트. k6의 rerank_measure_failure < 1% 임계가 설계대로 나온 503 거절까지 실패로 센다(60/s에서 33.7%). 부하 차단이 있는 시스템을 재려면 "올바른 거절"과 "실패"를 구분해야 한다.
  • 온라인 피처 캐시. 한 요청 안에서 유저 피처는 후보 전체에 공통인데 매번 다시 읽는다. 로컬에서는 조회 비중이 작지만 GKE에서는 다르다.

재현 방법

uvicorn applications.reranking_api.app:app --host 127.0.0.1 --port 8000
  RERANK_MAX_CONCURRENCY=4  RERANK_REQUEST_TIMEOUT_SECONDS=1.0

k6 run -e LOAD_MODE=open -e ARRIVAL_RATE=<rate> -e CANDIDATE_COUNT=200 \
       -e WARMUP_SECONDS=8 -e MEASURE_SECONDS=25 \
       applications/reranking_api/loadtest/rerank.js
